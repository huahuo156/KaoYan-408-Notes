# 第五章 传输层
## 传输层提供的服务
### 传输层的功能
1. 应用<mark style="background:#40a9ff">进程之间</mark>的逻辑通信/<mark style="background:#40a9ff">端到端</mark>的逻辑通信
2. 复用和分用
	1. 复用：指发送方的多个应用可以使用同一个传输层协议传送数据
	2. 分用：指接收方的传输层在剥去报文首部后，能将数据正确交付给对应的目的应用进程
3. 差错检查：会对整个报文(首部+数据部分)进行差错检查，而 <mark style="background:#40a9ff">IP 数据报仅对 <mark style="background:#d3f8b6">首部</mark> 进行差错检查</mark>
	1. TCP 连接，接收方发现差错，要求发送方重传报文
	2. UDP 连接，接收方发现差错，直接丢弃，不要求重传
4. **提供面向连接和无连接的传输服务**

### 传输层的寻址与端口
1. 端口的作用：是传输层与应用层交互的接口
2. 端口号：
	1. <mark style="background:#40a9ff">应用进程通过 <mark style="background:#d3f8b6">端口号</mark> 标识</mark>，端口号长度为 <mark style="background:#d3f8b6">16 bit</mark>(范围为 $2^{16}=65536$ 个端口号)
	2. <mark style="background:#40a9ff">端口号仅具有本地意义</mark>，不同主机的相同的端口号是没有关联的，且 TCP、UDP 的端口号彼此也是独立的
	3. 进程标识
		1. TCP：<源主机 IP 地址，源主机端口号，目的主机 IP 地址，目的主机端口号>
		2. UDP：<目的主机 IP 地址，目的主机端口号>
	4. 分类：
		1. **服务器**使用的端口号：
			1. <mark style="background:#fff88f">熟知端口：范围 0~1023，分配给重要的 TCP/IP 应用程序</mark>
			2. 登记端口号：范围 1024~49151
		2. **客户端**使用的端口号：范围 49152~65535，在<mark style="background:#fff88f">使用时动态分配</mark>
3. 套接字/Socket：<IP 地址：端口号>，唯一标识网络中某台主机上的一个应用进程

## UDP
### UDP 数据报
1. UDP 协议的特点
	1. 是<mark style="background:#40a9ff">无连接的</mark>：没有建立连接的时延
	2. <mark style="background:#40a9ff">不保证可靠交付</mark>
	3. <mark style="background:#40a9ff">面向报文的</mark>：<mark style="background:#fff88f">一次发送一个完整的报文，既不合并也不拆分，而是保留报文的边界</mark>
	4. <mark style="background:#40a9ff">首部开销小：仅有 8 B</mark>
	5. 支持 一对一、一对多、多对多 的通信
	6. <mark style="background:#40a9ff">没有拥塞控制</mark>
	7. <mark style="background:#fff88f">广泛用于多媒体应用</mark>
2. UDP 的首部格式：4 个字段，每个字段均为 2 B 大小
	1. **源端口号**：不需要回复时可置为 全 0
	2. **目的端口号**：该字段必须有效
	3. **长度**：整个报文的长度(**首部+数据**)
	4. **检验和**：检验整个报文，置为 全 0 表示不使用该字段

### UDP 检验
1. <mark style="background:#d3f8b6">伪首部：12 B，仅临时用于该 UDP 数据报的校验和计算</mark>，组成：
	1. 源/目的 IP 地址
	2. 1 B 全 0
	3. 1 B 表示 “17” 二进制数
	4. UDP 长度，与首部中的 UDP 字段的值保持一致
2. 计算过程：
	1. 发送方：
		1. 校验和字段全置为 0，伪首部与数据报 <mark style="background:#d3f8b6">每 16 bit 划分为一组</mark>；若数据报长度为奇数个字节则补充 全 0 的 1B
		2. <mark style="background:#d3f8b6">所有 16 bit 组先取反码再求和</mark>，并<mark style="background:#d3f8b6">将结果的反码填入校验和</mark>字段后发送
	2. 接收方：
		1. 将收到的 UDP 数据报与伪首部重新组合，再二进制反码规则求和；<mark style="background:#d3f8b6">若无差错，则结果为全 1</mark>；否则直接丢弃该报文
3. 与 IP 数据报的校验和的区别：IP 数据报的校验和仅 校验 IP 数据报的首部


## TCP
### TCP 的特点
1. <mark style="background:#40a9ff">面向连接</mark>
2. <mark style="background:#40a9ff">可靠数据传输</mark>
3. <mark style="background:#40a9ff">仅支持一对一数据传输</mark>
4. <mark style="background:#40a9ff">全双工通信</mark>
5. <mark style="background:#40a9ff">面向字节流</mark>，即使逻辑上是来自进程的不同数据段的字节数据仍可以放置在同一个 TCP 数据报中

### TCP 报文段
1. ~~源/目的端口~~
2. **序号/seq**，占 4B，范围为 $0\sim2^{32}-1$，并且循环使用；TCP 连接为传送中的每个字节都按顺序编号，序号字段的值表明了本报文段所发送数据的第一个字节的编号
3. **确认序号/ack/ack_seq**，占 4B，表示期望收到对方下一个报文段中第一个数据字节的序号。若确认序号为 N 表示到序号 N-1 为止的所有数据均已正确接收，采用 累计确认 机制
4. **数据偏移/首部长度**，占 4 bit，用于指出 TCP 首部的长度；偏移单位为 4B，即 TCP 的首部长度为 4B 的整数倍，且范围为 20B~60B
5. ~~保留~~，占 6 bit
6. ~~紧急位/URG~~，当 URG = 1 时，表示紧急指针字段有效，通知系统本报文段中包含紧急数据，应优先处理/插队传输
7. **确认位/ACK**，仅当 ACK = 1 时，确认序号字段才有效；TCP 规定在建立连接后，所有传送的报文段都必须将 ACK 置为 1。仅仅在 握手 1 报文中 ACK = 0，其余为 1
8. ~~推送位/PSH~~，在交互通信中，应用进程希望输入命令后能立即收到响应
9. **复位位/RST**，当 RST = 1 时，表示 TCP 连接出现严重差错，必须释放连接并重新建立连接；或者用于拒绝非法报文段或连接请求
10. **同步位/SYN**，当 SYN = 1 时，表示这是一个连接请求或连接接收报文。仅仅在 握手 1/2 报文中 SYN = 1，其余为 0
11. **终止位/FIN**，当 FIN = 1 时，表示此报文段的发送方已无更多的数据要发送，并请求释放连接(单方向)。仅 挥手 1/3 报文 FIN = 1，其余为 0
12. **窗口**，占 2B，以字节为单位，由本报文段的发送方填写，表示器作为接收方时当前还能接收的最大数据量，用于实现“端到端的流量控制”
13. **检验和**，占 2B，与 UDP 校验和类似：添加临时的 12 B 伪首部，但协议字段由 17 改为 6
14. ~~紧急指针~~
15. ~~选项~~，可用于协商 MSS
16. ~~填充~~

### TCP 的连接管理
1. TCP 连接的建立：“三次握手”
	1. 握手 1(C->S)：SYN = 1,ACK = 0,seq = x(初始序号，发送方自行决定，并消耗一个序号),ack_seq(无效) \[禁止携带数据\]
	2. 握手 2(S->C)：SYN = 1,ACK = 1,seq = y(消耗一个序号),ack_seq = x+1 \[禁止携带数据\]
	3. 握手 3(C->S)：SYN = 0,ACK = 1,seq = x+1,ack_seq = y+1 (可携带数据，并消耗序号；不携带数据，则不消耗序号)
2. TCP 连接的释放：“四次挥手”
	1. 挥手 1(C->S)：FIN = 1,ACK = 1,seq = u(消耗一个序号；可携带数据，但实际中一般不携带数据)
	2. 挥手 2(S->C)：FIN = 0,ACK = 1,seq = v,ack_seq = u+1(消耗一个序号；不可携带数据)
	3. 挥手 3(S->C)：FIN = 1,ACK = 1,seq = w,ack_seq = u+1(消耗一个序号；可携带数据，但实际中一般不携带数据)
	4. 挥手 4(C->S)：FIN = 0,ACK = 1,seq = u+1,ack_seq = w+1
	5. C 等待 2 MSL 进入 CLOSE 状态
		1. 确保客户发送的最后一个 ACK 报文能够到达服务器
		2. 使本连接中所有可能滞留的旧报文从网络中自然消失，避免影响新连接

### TCP 可靠传输
1. 序号：用于保证数据按序提交给应用层
2. 确认：表示期望收到对方下一个报文段中第一个数据字节的序号，默认采用累计确认机制
3. 重传：
	1. 超时：为每个报文段设置计时器；计时器到期仍未收到确认时，重传该报文
	2. 冗余 ACK：是再次确认某个报文段的 ACK，而发送方先前已经收到过该报文段的确认
	3. 快速重传机制：当发送方接收到对同一个报文段的 3 个冗余 ACK 时，可认为紧接该确认报文段之后的报文段已经丢失，并重传后续报文

### TCP 流量控制
使用 窗口字段 实现，发送方的发送窗口不得超过接收方给出的接收窗口值
若窗口值减为 0，则发送方设置一个 持续计时器，只要收到对方的零窗口通知，就启动持续计时器。若计时器超时则发送一个 零窗口探测报文段，而对方会在确认该探测报文时给出当前的窗口值。若窗口值仍为 0，重新设置计时器；否则可以数据传输

### TCP 拥塞控制
1. 拥塞控制与流量控制的区别：
	1. 拥塞控制是全局性的
	2. 流量控制是端到端的
2. 发送窗口的大小：min(接收窗口，拥塞窗口)，通常以 MSS 为单位

#### 慢开始与拥塞避免
1. 慢开始阶段：
	1. 初始拥塞窗口/cwnd 为 1 MSS，并每收到一个对新报文的确认，就将 cwnd 加 1。实现了每经过一个 传输轮次/RTT，cwnd 就会加倍，从而随传输轮次呈 指数增长
	2. 设置一个 慢开始门限/阈值 ssthresh：当 cwnd 增长至 ssthresh 时，停止慢开始算法，转而采用拥塞避免算法
2. 拥塞避免阶段：
	1. 每经过一个 传输轮次/RTT，就将 cwnd 加 1，而不是加倍，实现线性增长
3. 网络拥塞处理：出现超时现象
	1. 将慢开始门限 ssthresh 设置为 当前 cwnd 的一半(但不小于 2)
	2. 将 cwnd 设置为 1
	3. 重新执行 慢开始算法

#### 快重传与快恢复
1. 快重传：采用立即确认机制，当收到 3 个相同的冗余 ACK 时，立即重传
2. 快恢复：收到 3 个相同的冗余 ACK 时
	1. 将 ssthresh 设置为当前 cwnd 的一半
	2. 将 cwnd 设置为 ssthresh
	3. 重新执行 拥塞避免算法
